1. PROJECT OVERVIEW
================================================================================

WebSentinel is a full-stack web security dashboard that enables security analysts
to perform subdomain enumeration, TLS/certificate inspection, security header
analysis, and generate comprehensive PDF security reports — all from a browser-
based interface with no terminal access required.

The project is structured as a pnpm monorepo deployed across two platforms:
  - Render       : Hosts the Express API server (Node.js backend)
  - Vercel       : Hosts the React frontend (Vite static build)
  - Firebase     : Persistence layer (Firestore) for production data

The system aggregates data from 8 passive OSINT APIs and 3 binary enumeration
tools, runs DNS brute-force, and resolves found subdomains — all orchestrated
through a single authenticated API endpoint.

2.1 High-Level Overview

Communication:
  Frontend <--HTTPS/JSON--> API Server <--TCP/HTTPS--> External APIs & DNS

2.2 API Server Architecture
----------------------------
Framework  : Express v5 (ESM)
Port       : 3000
Build      : esbuild bundles src/ into dist/index.mjs (~1.6 MB single file)

Middleware stack (in order):
  1. pino-http       Request/response structured logging (redacts auth headers)
  2. Security headers X-Frame-Options, X-Content-Type-Options, HSTS, CSP,
                      Referrer-Policy
  3. CORS            Explicit origin allowlist via CORS_ORIGINS env var
  4. express.json    JSON body parsing
  5. express.urlencoded URL-encoded body parsing
  6. /api router     All application routes

API Route Map:
  GET  /api/healthz                    Health check (no auth)
  POST /api/auth/login                 Authenticate user, return bearer token
  POST /api/auth/logout                Invalidate session token
  GET  /api/auth/me                    Return current user profile
  POST /api/subdomains/enumerate       Run full subdomain scan (requires auth)
  POST /api/tls/check                  Run TLS/certificate analysis (requires auth)

Authentication:
  - Bearer token strategy
  - Tokens stored in in-memory Map (activeSessions)
  - requireAuth middleware protects scan endpoints
  - Firebase Admin SDK used for production user management

3. FEATURES (FULLY WORKING)
================================================================================

3.1 Subdomain Enumeration
--------------------------
Triggered via POST /api/subdomains/enumerate.

Pipeline stages:
  Stage 1+2 — Parallel passive intelligence gathering:

    Passive API Sources (8 total, all running in parallel):
      crt.sh          Certificate Transparency logs (no auth)
      HackerTarget    Host search API (100 req/day free tier)
      RapidDNS        Subdomain database (HTML scrape)
      AlienVault OTX  Passive DNS data (rate limited on large domains)
      ThreatCrowd     Threat intelligence (may time out occasionally)
      VirusTotal      Domain report (requires VT_API_KEY env var)
      URLScan.io      Browser scan history
      Anubis-DB       Passive subdomain database

    Binary Tool Runners (3 total, all running in parallel):
      Subfinder       Go binary (bin/subfinder.exe, ~30 MB)
      Amass           Go binary (bin/amass.exe, ~51 MB)
      Sublist3r       Python script (pip install sublist3r)

  Stage 3 — Built-in prefix guessing (14 common prefixes: www, mail, api, etc.)
  Stage 4 — DNS brute-force with configurable wordlist (batches of 15)
  Stage 5 — DNS resolution (A, AAAA, CNAME) + optional HTTP probe

  Response fields per subdomain:
    fqdn, resolved, ipAddresses, source, sources[], httpStatus,
    httpsAvailable, responseTime, cnames

3.2 TLS / Certificate Analysis
--------------------------------
Triggered via POST /api/tls/check. All checks run in parallel.

  Certificate inspection:
    tls.connect -> getPeerCertificate -> parse subject, issuer, SANs,
    validity dates, fingerprint, self-signed flag, wildcard detection

  Security headers check:
    https.request GET / -> collect response headers
    Parse HSTS (max-age, includeSubDomains, preload)
    http.request HEAD :80 -> check HTTP-to-HTTPS redirect

  TLS version probing:
    4x tls.connect with pinned min/max version
    Checks support for: TLS 1.0, 1.1, 1.2, 1.3

  Grading algorithm:
    Starts at 100, deducts points for:
      - Certificate expiring soon or expired
      - Self-signed certificate
      - Deprecated TLS versions (1.0, 1.1) enabled
      - Missing security headers (HSTS, X-Frame-Options, etc.)
      - No HTTP-to-HTTPS redirect

  Response: { host, cert, securityHeaders[], httpsRedirect,
              tlsSupport, overallGrade, findings[], elapsedMs }

3.3 PDF Report Generation
--------------------------
Fully client-side — no server round-trip. Uses jsPDF + jspdf-autotable.

12 configurable report sections:
  1.  Cover page (classification banner, metadata)
  2.  Executive summary (stat boxes, security posture narrative)
  3.  Subdomain enumeration (asset inventory, source breakdown table)
  4.  Certificate transparency (CT-sourced hostnames, wildcards)
  5.  DNS analysis (IP mapping, CNAME takeover, dangling records)
  6.  HTTPS/TLS assessment (cert details, version support matrix, HSTS)
  7.  Security headers (per-header pass/fail + recommendations)
  8.  Findings (per-severity list with IDs, impact, evidence)
  9.  Risk assessment (scoring methodology, per-domain scores)
  10. Mitigation (remediation steps, responsible teams, timelines)
  11. Analytics (score trends, discovery stats, compliance rates)
  12. Appendices (execution log, tool versions, limitations)

3.4 Authentication
-------------------
  Login      : POST /api/auth/login with email + password
  Session    : Bearer token stored in localStorage, validated per-request
  Logout     : Invalidates session token server-side
  Demo users :
    admin@websentinel.io / demo1234  (Security Analyst role)
    demo@websentinel.io  / demo      (Viewer role)
  Production : Firebase Admin SDK for real user management

3.5 Workspace Management
--------------------------
  Users can create named workspaces (e.g. per-client, per-project).
  Each workspace has its own isolated scan history (max 50 records, FIFO).
  Switching workspaces updates all views to show only that workspace's data.

3.6 Scan History
-----------------
  All subdomain and TLS scans are saved automatically per workspace.
  Users can view, delete individual records, or clear all history.
  Each record stores the full raw API response for re-inspection.
  Max 50 records per workspace (oldest removed automatically).

6. SECURITY POSTURE
================================================================================

6.1 Implemented Controls
--------------------------
  Input validation    : Zod safeParse() on all API route bodies
  Domain validation   : RFC-compliant regex on domain/host inputs
  CORS restriction    : Explicit origin allowlist (CORS_ORIGINS env var)
  Security headers    : X-Frame-Options, X-Content-Type-Options, HSTS,
                        Content-Security-Policy, Referrer-Policy
  Log redaction       : pino-http strips Authorization and Cookie headers
  Auth protection     : requireAuth middleware on all scan endpoints
  HTTPS               : Enforced by Render and Vercel platforms

6.2 Prototype Limitations (not production-ready)
--------------------------------------------------
  Password hashing    : DEMO_USERS stores plaintext passwords
  Token generation    : Uses Math.random() (not cryptographically secure)
  Token expiry        : activeSessions entries never expire
  Token storage       : localStorage (XSS-accessible; HttpOnly cookie preferred)
  Rate limiting       : No brute-force protection on auth endpoints
  Session store       : In-memory Map (resets on restart)

6.3 Production Upgrade Path
-----------------------------
  1. Hash passwords with bcrypt
  2. Replace Math.random() tokens with crypto.randomBytes()
  3. Add TTL to sessions or switch to signed JWT with expiry
  4. Move token to HttpOnly cookie
  5. Add express-rate-limit to auth routes
  6. Connect @workspace/db (Drizzle + PostgreSQL) for persistent sessions/users
  7. Move scan history from localStorage to API-backed per-user records
